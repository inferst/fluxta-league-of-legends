# Windows runbook: issue #1

Цель — проверить плагин через публичный интерфейс Fluxta и зафиксировать
реальные контракты локальных API. Прохождение автоматических тестов не заменяет
этот runbook. Начальный статус всех пунктов: **не выполнено**.

Зафиксирован [частичный результат windows-session-02](observations/2026-11-03-windows-session-02.md):
один реальный матч Solo/Duo, проверенные входные данные аккаунта/рангов/составов,
lifecycle и нативных событий. В отчёте отдельно указаны оставшиеся проверки;
он не закрывает весь runbook.

Также зафиксирован [результат windows-session-03](observations/2026-11-03-windows-session-03.md):
реальный матч Flex, независимое обновление Flex-ранга и нативный `GameEnd / Win`.
Полный исходник проверен; прежний game id и составы сохраняются в LCU после
возврата в Lobby.

Зафиксирован [результат windows-session-04](observations/2026-11-03-windows-session-04.md):
normal draft, очередь 400; оба ranked inputs остаются неизменными. После матча
Lobby возвращает queue 440 со старым game id и составами; исходник проверен
полностью. Теперь игровые прогоны есть для всех трёх требуемых семейств очередей.
Остальные сценарии и точное сопоставление с экраном загрузки ещё не подтверждены.

[Ручное подтверждение переходов аккаунта и перезапусков](observations/2026-11-03-manual-account-recovery.md)
фиксирует выход с `absent / unavailable`, повторный вход и восстановление после
перезапусков League и Fluxta, а также изменение значения при смене аккаунта.
Проверка маркером также подтверждена: при `absent` остаётся `SOURCE_ABSENT`, а
после открытия клиента записываются значения аккаунта. Старая identity в Global
Variables объясняется пропущенным присваиванием отсутствующего Source.

[Сессия 05](observations/2026-11-03-windows-session-05.md) записывает переход
`None → Lobby` для Solo/Duo без игры. Один запрос аккаунта не удался, при этом
клиент остался доступен, а аккаунт восстановился в следующем цикле. Исходник и
вся выборка проверены; контролируемый сбой всего локального API ещё не проверен.

В текущем согласованном объёме два пункта [явно пропущены](observations/2026-11-03-manual-account-recovery.md#explicitly-skipped-checks-for-this-verification-pass):
контролируемый сбой всего локального API отложен, а unranked не проверяется из-за
отсутствия подходящего аккаунта. Их статус — «не выполнялось» с указанной причиной;
это не подтверждение поведения и не требование выполнить эти пункты сейчас.
Контракт unranked остаётся неизвестным: отсутствие записи, нулевые LP или ошибка
API сами по себе не доказывают отсутствие ранга.

[Итог согласованной проверки](observations/2026-11-04-verification-summary.md)
объединяет реальные captures и ручные подтверждения. Согласованные ручные
действия завершены; пропуски и неизмеренные детали остаются явно отмеченными.

## 1. Подготовка

Нужны Windows 10/11, установленный League of Legends, Fluxta >=0.9.0,
Node >=22.18.0, pnpm 10.34.3 и Git. Fluxta и League запускаются на одном
компьютере, под одним пользователем, сначала без повышения прав.
Riot API key не нужен.

Для повторяемого полуавтоматического прогона из подготовленного checkout
запустите Fluxta, оставьте League закрытым и выполните:

```powershell
pnpm verify:windows --out captures/windows-session-01 --seconds 3600
```

Команда собирает runner, выполняет `pnpm check`, регистрирует Development Link,
перезапускает плагин через опубликованный CLI и запускает описанный ниже capture.
Вход/выход, смену аккаунта, запуск матчей и заметки UTC выполняйте вручную во время
записи. По истечении времени или Ctrl+C runner создаёт `report.md` с перечнем
наблюдений и оставшихся ручных проверок. `session.json` содержит commit,
признак изменённого checkout, версии среды и результат подготовки. Если подготовка
остановилась, причина указана этапом в `failedStage`; используйте новую папку при
повторном запуске. Локальные пути, ошибки HTTP и реальные identity туда не копируются.

`--capture-only` явно пропускает подключение к Fluxta. Для формирования отчёта по
существующему JSONL без запуска клиента/Fluxta используйте:

```powershell
pnpm verify:windows --input captures/windows-session-01/capture.jsonl --out captures/windows-summary-01
```

В CLI 0.8.2 нет публичной команды чтения Sources и External Connections из
хоста. Поэтому runner проверяет загрузку процесса плагина, но значения из
раздела 2 подтверждаются отдельно в интерфейсе. Сводка состояний capture не
заменяет эту проверку. Полнота составов и соответствие рангов также остаются
предметом анализа по разделам ниже. Автоматический отчёт всегда частичный;
пропущенные проверки нельзя считать пройденными.

Для подготовки и выполнения шагов по отдельности:

```powershell
git clone https://github.com/inferst/fluxta-league-of-legends.git
cd fluxta-league-of-legends
git switch feat/local-client-acquisition
git rev-parse HEAD
node --version
pnpm --version
pnpm install --frozen-lockfile
pnpm check
```

Если checkout уже есть, используйте ветку/commit проверяемого PR. Скопируйте
[шаблон результата](windows-results-template.md) в новый Markdown-файл и укажите
commit, версию Windows (`winver`), видимую версию клиента/патча и версию Fluxta.
В capture дополнительно попадут версия Node, Windows release и ответ локального
endpoint версии, если он доступен. Не заменяйте видимую версию словом «latest».

Запустите Fluxta и зарегистрируйте Development Link:

```powershell
pnpm exec fluxta link dist/league-of-legends
pnpm exec fluxta link --status
```

Если Development Link был зарегистрирован как `lol`, перед новой привязкой
выполните `pnpm exec fluxta unlink lol`. В существующих тестовых сценариях заново
выберите Sources плагина `league-of-legends`. Старые отчёты сохраняют прежний id,
с которым выполнялись проверки.

Проверьте, что плагин **League of Legends** запущен. В стандартном индикаторе
External Connections должна быть одна запись **League of Legends**. Её id
`local-client` остаётся постоянным при входе, выходе и перезапуске клиента.
Этот индикатор проверяется без создания Item.

## 2. Проверка публичных Sources

Для чтения Sources создайте временный сценарий/кнопку с Set Variable, выбирая
источники плагина в редакторе значения. Используйте отдельные Global Variables
для `league-of-legends.clientState`, `league-of-legends.clientAvailable`, `league-of-legends.accountState`, `league-of-legends.accountId`,
`league-of-legends.accountName` и `league-of-legends.observedAt`. Для проверки состояний также подойдёт If
Else с соответствующим источником. Имена в интерфейсе приведены в README.

Запускайте сценарий после каждого перехода. Отсутствующий Source может оставить
предыдущее значение Global Variable: проверяйте его отсутствие условием, а не
считайте оставшуюся переменную текущим аккаунтом. Не публикуйте реальные PUUID,
Riot ID или снимки экрана с ними; в отчёте достаточно «совпадает/не совпадает».

Для однозначной проверки отсутствия `accountId`/`accountName` после выхода:

1. Убедитесь, что `clientState` уже `absent`.
2. Присвойте обеим тестовым Global Variables литерал `SOURCE_ABSENT`.
3. Выполните только два Set Variable, читающих `league-of-legends.accountId` и `league-of-legends.accountName`.
4. Если маркер остаётся, Source не дал значения для присваивания. Если вместо
   маркера вернулась старая identity, это воспроизведение устаревших данных в
   реальном host-пути, которое нужно отдельно исследовать.

В обычном сценарии сначала явно присваивайте обеим переменным литерал
`NO_ACCOUNT`, затем читайте Sources. Так отсутствие значения оставит понятный
маркер, а не предыдущую identity. При необходимости используйте явно заданную
пустую строку вместо маркера. Сбрасывайте обе переменные перед каждым чтением:
даже при `identified` Source полного Riot ID может отсутствовать. Не заменяйте
отсутствующий Source пустой строкой внутри плагина ради сброса Global Variables.

| Действие                                  | Ожидаемые Sources                                                                                                                                                 | External Connection           |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- |
| Полностью закрыть League, оставить Fluxta | `absent`, `false`, `unavailable`; account Sources отсутствуют                                                                                                     | Отключено                     |
| Запустить League и войти                  | `available`, `true`, `identified`; PUUID и полный Riot ID соответствуют текущему аккаунту                                                                         | Подключено                    |
| Оставить клиент в меню без игры           | Клиент по-прежнему `available`; аккаунт определён                                                                                                                 | Подключено                    |
| Выйти из аккаунта                         | Предыдущие account Sources исчезают; при оставшемся доступном LCU — `unidentified` либо `unavailable` согласно реальному ответу; если процесс закрылся — `absent` | Соответствует доступности LCU |
| Повторно войти / сменить аккаунт          | Определяется текущий аккаунт; данные старого не подставляются                                                                                                     | Подключено                    |
| Закрыть и снова открыть League            | Переход через отсутствие/недоступность, затем автоматическое восстановление без настройки порта/пароля                                                            | Восстанавливается             |
| Перезапустить Fluxta при открытом League  | Свежая доступность и аккаунт появляются заново                                                                                                                    | Восстанавливается             |

Короткое `checking` допустимо до первого наблюдения. Обычно переход виден за
несколько секунд; discovery ограничен 5 секундами, HTTP-запрос — 1.5 секунды,
после завершения цикла пауза 1 секунда. Запишите фактическую задержку и поведение
при запуске/выходе. Если при выходе LCU исчезает целиком, это не доказательство
проверки ветки «доступный, но неопределённый аккаунт»: отметьте её отдельно.

Проверка временной недоступности выполняется **в меню, вне матча и поиска**.
Если доступен Windows Resource Monitor, временно приостановите
`LeagueClient.exe` (локальный API), оставив `LeagueClientUx.exe` обнаруживаемым.
Через 10 секунд проверьте `inaccessible`, `false`, `unavailable`, отсутствие
старого аккаунта и отключённый индикатор. Возобновите процесс и проверьте
автоматическое восстановление. Не оставляйте процесс приостановленным. Если
операция недоступна или API не остановился, запишите «не выполнено» с причиной;
отключение интернета не проверяет недоступность loopback API.

## 3. Сбор наблюдений тем же путём подключения

До запуска League начните запись в отдельном PowerShell из корня checkout:

```powershell
pnpm capture --out captures/session-01.jsonl --seconds 3600
```

Файл создаётся заново; существующий не перезаписывается. Для следующего прогона
выберите другое имя. Ctrl+C завершает запись с сохранением полных JSONL-строк.
Сборщик не требует запущенной Fluxta; он использует тот же модуль discovery,
HTTP и интерпретации аккаунта, добавляя probes рангов/матча. Проверка Sources в
Fluxta из раздела 2 нужна отдельно.

Ведите короткую временную шкалу UTC: запуск, вход, выход, очередь, champion
select, начало экрана загрузки, появление карты, конец матча, закрытие клиента.
В PowerShell текущее UTC можно записать командой:

```powershell
[DateTime]::UtcNow.ToString("o")
```

Сборщик сохраняет `startedAt`/`finishedAt` для каждого запроса. Один кадр состоит
из нескольких запросов и **не является атомарным Match Snapshot**. Первый
зафиксированный ответ ограничивает точность измерения периодом опроса; не
выдавайте его за точный момент появления данных на сервере.

Не снимайте discovery вручную командами, печатающими CommandLine, и не
добавляйте токены/Authorization в отчёт. Capture содержит только выбранные поля;
личные имена и идентификаторы заменены согласованными псевдонимами внутри файла.

После остановки записи можно подготовить компактный набор для анализа:

```powershell
pnpm capture:compact --input captures/session-01.jsonl --out captures/session-01-compact
```

Начинайте анализ с `summary.md`. В `evidence.jsonl` сохранены полные исходные
строки со значимыми изменениями и соседними кадрами; `evidence-index.jsonl`
содержит номера строк исходника, номера строк выборки и причины отбора.
`events.jsonl` содержит нативные события без повторяющихся наблюдений, с
исходными request timestamps и номерами строк; исправления одного EventID
сохраняются как ревизии. В полных соседних кадрах события могут повторяться.
Исходный файл не изменяется; в сводке сохраняются его SHA-256 и статистика
сокращения. `report.md` содержит базовый перечень наблюдений.

Отбор сохраняет изменения клиента/аккаунта, HTTP-статусов, ранговых inputs,
версии, lifecycle/очереди/game id, состава/идентификаторов/чемпионов/команд,
новые формы ответа и первый пример каждого типа события в сегменте наблюдения.
Тики времени/статистики/уровней/смертей сами по себе кадр не сохраняют.
По умолчанию сохраняется один сосед до и после изменения; `--context 0..5`
позволяет изменить это число. `pnpm verify:windows` также создаёт эти файлы
автоматически после завершения записи.

Сегмент событий — консервативная граница по наблюдаемой смене game id,
откату Live clock/числа событий либо неоднозначному восстановлению Live API;
это не доказательство принадлежности ответов разных API одному матчу.
Пропуски, уже возникшие из-за окна последних 50 событий, восстановить нельзя;
возможные разрывы отмечаются в сводке. Выборка не подтверждает Roster Ready
автоматически. Для уточнения времени/полноты возвращайтесь к полному исходнику.
Синтетическое происхождение сохраняется. Используйте завершённую запись
коллектора и новую папку вывода; повреждённый или изменяющийся файл не создаёт
завершённой сводки. Перед передачей просмотрите отобранные данные.

## 4. Контракты аккаунта, рангов и lifecycle

В JSONL проверьте `requests[]` по `endpoint` и `status`:

- `/lol-summoner/v1/current-summoner`: когда появляется PUUID; доступны ли
  `gameName` и `tagLine`; что приходит до входа и после выхода. Сопоставьте
  обезличенный аккаунт с `activePlayer` и участником игры без догадок по порядку.
- `/lol-ranked/v1/current-ranked-stats`: независимые записи Solo/Duo
  (`RANKED_SOLO_5x5`) и Flex (`RANKED_FLEX_SR`), формат `queues`/`queueMap`,
  `tier`, `division`, `leaguePoints`. Сверьте оба ранга с клиентом. Отдельно
  проверьте доступный unranked аккаунт/очередь: отсутствие записи, `NONE`, пустой
  ответ и HTTP-ошибка должны быть описаны как разные наблюдения. Не считайте
  отсутствующий ранг unranked без фактического контракта.
- `/lol-gameflow/v1/gameflow-phase` и `/lol-gameflow/v1/session`: фактические
  lifecycle-строки, map, mode, queue id/type и стабильный game id. Запишите
  переходы от меню до завершения матча и возврата в меню.

Выполните отдельные прогоны для normal Summoner's Rift, Solo/Duo и Flex.
Укажите точный вариант normal queue. Если нет доступа к очереди или аккаунту,
отметьте пропуск явно. Practice/custom подходят для дополнительного исследования
полей, но не заменяют evidence поддерживаемых очередей.

## 5. Полнота составов и первый момент готовности

Для каждой проверяемой очереди сравните наблюдения во время загрузки и после
входа на карту:

1. В LCU session найдите обе команды, их финальные `championId` и устойчивые
   идентификаторы участников. Hover из champion select не считается финальным.
2. В Live Client `allPlayers` найдите все десять участников, их чемпионов и
   `team`. Проверьте, однозначно ли `activePlayer` связан с текущим аккаунтом и
   участником, а значит определены союзники и противники.
3. Зафиксируйте первый ответ, где **обе** полные команды и личность стримера
   доступны. Запишите request timestamps, фактическую lifecycle-стадию и
   `gameData.gameTime`, если он уже есть. Если данные из разных API, укажите
   оба времени; не объединяйте ответы разных матчей.
4. Отдельно перечислите недоступные поля: роли, идентификаторы, противники,
   чемпионы или любые детали, которые реально отсутствуют.

Если полный состав на загрузке недоступен, это допустимый результат исследования:
запишите ограничение и первый полный ответ **после входа на карту** с реальным
game time. Это принятый fallback для следующего тикета. Если состав остаётся
неполным или личность не удаётся связать — готовность не подтверждена.
Случайный порядок участников и похожие имена не заменяют устойчивую связь.

## 6. Нативные игровые happenings

В `events.Events` перечислите фактически наблюдавшиеся `EventName`, `EventID`,
`EventTime` и дополнительные поля. Capture оставляет последние 50 событий в
каждом ответе, `_totalEvents` показывает исходное число. Для редких событий
нужен кадр рядом со временем их возникновения.

Проверьте доступные примеры начала/конца игры, убийства чемпиона, разрушения
башни/ингибитора, убийства dragon/herald/baron. Не нужно специально менять
поведение в обычном матче ради события. Ненаблюдавшиеся типы отметьте как
непроверенные. Список полей в `_observedKeys` не гарантирует, что все их значения
сохранены. По отсутствующим событиям не делайте вывод, что API их не поддерживает.

## 7. Сохранение результата

1. Заполните [шаблон](windows-results-template.md), включая пропуски и ошибки.
2. Просмотрите capture перед передачей: реальные Riot ID/PUUID, локальные пути,
   command lines и секреты в нём отсутствуют. Не отправляйте raw-ответы API.
3. Сохраните небольшой репрезентативный набор полных строк: header, меню,
   два ranked inputs, загрузка, первый полный состав, игра с happenings,
   завершение, закрытие/восстановление. Сохраните исходные timestamps и
   `_observedKeys`; не меняйте provenance и не выдавайте synthetic fixture за
   реальное наблюдение. Для порядка переходов сохраните соседние кадры.
4. После ревью поместите отчёт и примеры в `docs/acquisition/observations/`,
   обновите [findings](findings.md) и issue #1. Файлы `captures/` намеренно
